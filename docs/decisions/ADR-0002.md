# Context

A Operational Intelligence Platform (OIP) foi concebida para operar em ambientes críticos, como:

- Centrais Integradas de Emergência;
- Centros de Operações Urbanas;
- Segurança Pública;
- Defesa Civil;
- Segurança Patrimonial;
- Smart Cities;
- Indústria;
- Logística.

Nesses ambientes, milhares de eventos podem ocorrer simultaneamente.

Exemplos:

- uma câmera detecta um veículo;
- outra identifica a placa;
- outra reconhece a cor;
- um OCR identifica caracteres;
- um modelo ReID reconhece o mesmo veículo minutos depois;
- um detector de incêndio identifica fumaça;
- um modelo de áudio identifica um disparo;
- uma Capability de LLM classifica uma chamada.

Todas essas informações precisam coexistir.

Além disso:

- novas Capabilities devem ser adicionadas continuamente;
- nenhuma Capability deve conhecer outra;
- fornecedores externos devem conseguir desenvolver novas funcionalidades sem modificar a plataforma principal.

Uma arquitetura baseada em chamadas síncronas entre serviços criaria:

- alto acoplamento;
- dependências circulares;
- dificuldade de escalabilidade;
- aumento de latência;
- baixa tolerância a falhas;
- dificuldade para evolução independente.

Era necessário um modelo que permitisse crescimento praticamente ilimitado da plataforma sem perda de modularidade. Esse é um dos principais benefícios da EDA em sistemas distribuídos. :contentReference[oaicite:0]{index=0}

# Decision

Toda comunicação entre componentes da OIP será baseada em **Event-Driven Architecture (EDA)**.

Nenhum microsserviço poderá depender diretamente de outro para executar sua lógica de negócio.

A comunicação ocorrerá exclusivamente através do barramento de eventos.

O barramento oficial da plataforma é:

- **NATS JetStream**

Cada Capability atua como um componente independente que:

- consome eventos;
- produz novos eventos;
- desconhece quem produzirá ou consumirá esses eventos.

Assim, a plataforma passa a evoluir por composição de eventos e não por integração direta entre serviços.

---

# Princípios Arquiteturais

## Loose Coupling

Serviços nunca conhecem a implementação uns dos outros.

Conhecem apenas:

- contratos;
- schemas;
- eventos publicados.

---

## Event First

Toda mudança relevante de estado gera um evento.

Exemplos:

```
vehicle.detected
vehicle.tracked
plate.read
audio.transcribed
fire.detected
incident.created
incident.updated
dispatch.created
user.logged_in
```

O evento representa um fato ocorrido.

Nunca um comando.

---

## Event Immutability

Eventos publicados nunca são alterados.

Caso uma informação precise ser modificada, um novo evento deverá ser publicado.

Exemplo:

```
plate.read
↓

plate.corrected
```

Nunca:

```
UPDATE plate.read
```

---

## Publish Once

Cada Capability publica apenas os eventos que realmente produz.

Nunca republica eventos de terceiros.

---

## Independent Consumers

Qualquer serviço pode consumir um evento.

Sem necessidade de autorização do produtor.

Exemplo:

```
Vehicle Detector
        │
        ▼
vehicle.detected
        │
 ├──────────────┐
 ▼              ▼
OCR         ReID
 ▼              ▼
Correlation  Search
 ▼              ▼
Dashboard    Alert Engine
```

O produtor desconhece completamente quem consome o evento.

---

## Event Contracts

Todos os eventos são definidos em Protobuf.

Nunca por estruturas ad hoc.

Todos seguem:

- versionamento;
- compatibilidade retroativa;
- envelope canônico.

---

# Arquitetura Geral

```
Capability
      │
      ▼
+----------------------+
| NATS JetStream       |
+----------------------+
      │
      ├───────────────┐
      │               │
      ▼               ▼
Capability       Capability
      │               │
      ▼               ▼
Capability       Capability
      │               │
      └──────┬────────┘
             ▼
     Correlation Engine
             │
             ▼
      Knowledge Layer
             │
             ▼
      Search / Dashboard
```

Nenhuma seta horizontal representa comunicação direta.

Toda interação ocorre através do barramento.

---

# Event Categories

Os eventos são classificados em categorias.

## Operational Events

Representam fatos do domínio.

Exemplos:

- incident.created
- dispatch.finished
- camera.online

---

## AI Events

Representam inferências.

Exemplos:

- vehicle.detected
- plate.read
- face.detected

---

## Capability Events

Relacionados ao ciclo de vida das Capabilities.

Exemplos:

- capability.installed
- capability.started
- capability.failed

---

## Infrastructure Events

Produzidos pela plataforma.

Exemplos:

- node.joined
- storage.low
- gpu.overloaded

---

## Audit Events

Relacionados à rastreabilidade.

Exemplos:

- evidence.corrected
- user.login
- permission.changed

---

# Event Envelope

Todo evento deve utilizar o envelope definido pela OES.

Exemplo simplificado:

```yaml
id:
type:
source:
timestamp:
tenant:
entity:
payload:
metadata:
trace:
```

Isso garante padronização em toda a plataforma.

---

# Reliability

Todos os eventos críticos devem possuir:

- Persistência
- Acknowledgement
- Retry
- Dead Letter Queue
- Replay
- Ordering quando necessário

A confiabilidade é fornecida pelo NATS JetStream.

---

# Escalabilidade

Como consequência da EDA:

- serviços podem ser escalados individualmente;
- Capabilities podem ser adicionadas sem alterar serviços existentes;
- múltiplos consumidores podem surgir para um mesmo evento;
- novas integrações não exigem alterações no produtor.

---

# Benefícios

A adoção da Event-Driven Architecture proporciona:

- Baixo acoplamento
- Alta coesão
- Escalabilidade horizontal
- Resiliência
- Evolução independente
- Facilidade para plugins de terceiros
- Alta observabilidade
- Melhor rastreabilidade
- Facilidade de auditoria
- Reprocessamento de eventos
- Compatibilidade com Active Learning
- Compatibilidade com MLOps
- Compatibilidade com Data Lake
- Compatibilidade com Event Sourcing
- Compatibilidade com futuras arquiteturas distribuídas

---

# Consequences

## Positivas

- Arquitetura altamente modular.
- Capabilities totalmente independentes.
- Facilidade para desenvolvimento por terceiros.
- Escalabilidade praticamente ilimitada.
- Evolução incremental da plataforma.
- Melhor tolerância a falhas.
- Melhor governança dos contratos.
- Maior reutilização de componentes.

## Negativas

- Maior complexidade operacional.
- Necessidade de governança rigorosa dos eventos.
- Curva de aprendizado maior para novos desenvolvedores.
- Necessidade de observabilidade distribuída.
- Necessidade de versionamento cuidadoso dos contratos.

---

# Alternatives Considered

## REST síncrono entre microsserviços

**Rejeitado.**

Motivos:

- Alto acoplamento.
- Dependências circulares.
- Baixa escalabilidade.
- Dificuldade para plugins.

---

## gRPC direto entre serviços

**Rejeitado como mecanismo principal.**

Será utilizado apenas para:

- APIs administrativas;
- operações síncronas inevitáveis;
- consultas;
- Health Checks.

Nunca para propagação de eventos de domínio.

---

## Message Queue sem persistência

**Rejeitado.**

Não atende aos requisitos de:

- replay;
- auditoria;
- confiabilidade;
- recuperação de falhas.
