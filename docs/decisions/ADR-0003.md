# Context

A missão da **Operational Intelligence Platform (OIP)** é fornecer uma plataforma aberta e extensível para inteligência operacional em ambientes críticos.

Ao longo do tempo, novas necessidades surgirão:

- novos algoritmos de IA;
- novos equipamentos;
- novos sensores;
- novos protocolos;
- novos modelos de Machine Learning;
- novas integrações com PABX;
- novos módulos GIS;
- novos motores de OCR;
- novos modelos LLM;
- novos detectores.

Não é desejável que cada nova funcionalidade exija alterações na plataforma principal.

Isso criaria:

- aumento da complexidade;
- crescimento do repositório principal;
- dependências desnecessárias;
- ciclos longos de desenvolvimento;
- dificuldade para participação de terceiros.

Além disso, um dos objetivos estratégicos da OIP é criar um ecossistema onde empresas, universidades e desenvolvedores independentes possam produzir novas capacidades compatíveis com a plataforma.

Para isso, a arquitetura precisa ser pensada desde o início como uma plataforma extensível.

---

# Decision

A OIP adota oficialmente o princípio **Plugin First Architecture**.

Toda nova funcionalidade deverá ser desenvolvida preferencialmente como uma **Capability independente**, distribuída separadamente da plataforma principal.

A plataforma fornece apenas:

- Runtime;
- SDKs oficiais;
- contratos;
- barramento de eventos;
- infraestrutura;
- mecanismos de descoberta;
- gerenciamento do ciclo de vida.

Toda lógica especializada pertence às Capabilities.

---

# O que é uma Capability

Uma Capability representa uma unidade funcional independente capaz de produzir valor para a plataforma.

Ela pode:

- consumir eventos;
- produzir eventos;
- executar inferências;
- integrar equipamentos;
- enriquecer dados;
- disponibilizar APIs;
- gerar alertas;
- publicar métricas.

Ela não depende do código interno da plataforma.

---

# Arquitetura Geral

```
                +----------------+
                |     OIP        |
                |    Runtime     |
                +----------------+
                        │
                        │
        +---------------+---------------+
        │               │               │
        ▼               ▼               ▼
 Capability      Capability      Capability
   Vehicle          Audio            GIS

        ▼               ▼               ▼

 Capability      Capability      Capability
    OCR            LLM          Face Recognition

        ▼               ▼               ▼

 Capability      Capability      Capability
   Fire           Drone           PABX
```

A plataforma conhece apenas o contrato das Capabilities.

Nunca sua implementação.

---

# Core vs Plugins

A plataforma principal deve permanecer pequena.

## Core

Responsável apenas por infraestrutura.

Inclui:

- Runtime
- Event Bus
- Capability Manager
- Scheduler
- Security
- Authentication
- Authorization
- Observability
- Configuration
- Registry
- Dashboard Base

Todo o restante deve ser implementado como plugin.

---

## Plugins

Toda inteligência operacional pertence às Capabilities.

Exemplos:

- Vehicle Intelligence
- Plate Recognition
- Face Recognition
- Fire Detection
- Smoke Detection
- PPE Detection
- Person ReID
- Audio Classification
- Speech-to-Text
- NLP
- LLM Classification
- Dispatch Optimizer
- GIS Layers
- Drone Integration
- Radio Integration
- PABX Integration
- IoT Sensors
- Weather Integration

---

# Capability Independence

Uma Capability deve ser completamente independente.

Ela possui:

- repositório próprio;
- versionamento próprio;
- pipeline próprio;
- documentação própria;
- testes próprios;
- modelos próprios;
- configuração própria.

Não deve depender do código interno da plataforma.

A única dependência permitida é o SDK oficial.

---

# Comunicação

Capabilidades nunca chamam diretamente outras Capabilities.

Toda comunicação ocorre através de:

- eventos;
- contratos Protobuf;
- APIs públicas quando necessário.

Nunca por acesso direto ao código.

---

# Descoberta

A plataforma descobre automaticamente novas Capabilities.

Cada plugin publica um manifesto (`CSpec.yaml`) contendo informações como:

- nome;
- versão;
- fornecedor;
- eventos produzidos;
- eventos consumidos;
- requisitos de hardware;
- recursos utilizados;
- permissões necessárias.

O Runtime utiliza esse manifesto para registrar e gerenciar a Capability.

---

# Ciclo de Vida

Toda Capability segue o ciclo definido pela especificação **OCL**.

```
Installing

↓

Installed

↓

Starting

↓

Running

↓

Stopping

↓

Stopped

↓

Updating

↓

Running

↓

Deprecated

↓

Removed
```

O Runtime controla todas essas transições.

---

# Compatibilidade

Uma Capability não pode depender da versão da plataforma.

Ela depende apenas de:

- contratos públicos;
- SDK oficial;
- especificações.

Isso garante compatibilidade entre versões.

---

# Distribuição

As Capabilities são distribuídas separadamente.

Exemplos:

```
oip-capability-color

oip-capability-fire

oip-capability-ocr

oip-capability-drone

oip-capability-ppe
```

Cada repositório possui seu próprio ciclo de releases.

---

# Desenvolvimento por Terceiros

Qualquer organização pode desenvolver uma Capability.

Fluxo esperado:

```
Desenvolvedor

↓

SDK Oficial

↓

Implementa Capability

↓

Executa Testes

↓

Publica Imagem

↓

Publica Manifesto

↓

Capability Store

↓

Runtime instala automaticamente
```

Nenhuma alteração na plataforma principal é necessária.

---

# Capability Store

As Capabilities podem ser disponibilizadas em um repositório oficial.

Exemplo:

```
OIP Capability Store

├── IA
│   ├── Vehicle
│   ├── Fire
│   ├── Smoke
│   ├── OCR
│   └── Face
│
├── Integrações
│   ├── Cisco
│   ├── Asterisk
│   ├── SIP
│   └── MQTT
│
├── GIS
│
├── IoT
│
└── Utilitários
```

O Runtime consulta esse catálogo para instalação e atualização.

---

# Benefícios

A arquitetura Plugin First proporciona:

- baixo acoplamento;
- alta modularidade;
- escalabilidade funcional;
- evolução independente;
- menor risco de regressão;
- facilidade para desenvolvimento paralelo;
- facilidade para integração de fornecedores;
- reutilização de componentes;
- distribuição independente;
- inovação contínua.

---

# Responsabilidades da Plataforma

A plataforma principal é responsável por:

- descoberta de Capabilities;
- gerenciamento do ciclo de vida;
- autenticação;
- autorização;
- observabilidade;
- configuração;
- comunicação;
- armazenamento operacional;
- gerenciamento de eventos;
- auditoria;
- monitoramento.

Ela **não implementa inteligência de domínio**.

---

# Responsabilidades das Capabilities

Cada Capability é responsável por:

- sua lógica de negócio;
- inferência;
- integração externa;
- processamento;
- geração de eventos;
- documentação;
- testes;
- modelos de IA;
- configuração específica.

---

# Consequences

## Positivas

- Plataforma menor e mais simples.
- Crescimento praticamente ilimitado.
- Desenvolvimento paralelo por múltiplas equipes.
- Facilidade para participação da comunidade.
- Menor acoplamento entre componentes.
- Atualizações independentes.
- Melhor manutenção.
- Melhor reutilização.
- Ecossistema sustentável de extensões.

## Negativas

- Necessidade de forte governança das especificações.
- Necessidade de SDK estável.
- Maior investimento inicial em contratos.
- Processo de certificação de plugins.
- Controle rigoroso de compatibilidade entre versões.

---

# Alternatives Considered

## Arquitetura Monolítica

**Rejeitada.**

Toda nova funcionalidade exigiria alterações no núcleo da plataforma.

---

## Microsserviços internos apenas

**Rejeitada.**

Embora desacople serviços, continua exigindo alterações no ecossistema principal para adicionar novas capacidades.

---

## Plugins sem especificação oficial

**Rejeitada.**

Levaria à fragmentação do ecossistema, inconsistência entre implementações e baixa interoperabilidade.

# Status

**Accepted**

A partir desta decisão, toda nova funcionalidade da OIP deverá ser concebida sob a filosofia **Plugin First**, utilizando exclusivamente os contratos públicos, SDKs oficiais e especificações do ecossistema, preservando a independência entre a plataforma principal e as Capabilities.
